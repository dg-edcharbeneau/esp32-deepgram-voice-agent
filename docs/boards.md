# Boards

One firmware, two boards. The IDF target picks the board: there is one board
per chip, so nothing else needs choosing.

| | ESP32-S3 | ESP32-P4 |
|---|---|---|
| Board | Waveshare ESP32-S3-Touch-AMOLED-1.75C | Waveshare ESP32-P4-WIFI6-Touch-LCD-3.4C |
| Panel | 466 x 466 round AMOLED, CO5300 over QSPI | 800 x 800 round IPS, JD9365 over MIPI-DSI |
| Audio | ES8311 out, ES7210 in | the same two chips |
| Wi-Fi | on the chip | on an ESP32-C6, reached over SDIO |
| Battery | AXP2101 fuel gauge | none |
| BOOT button | GPIO 0 | GPIO 35 |
| Status | the reference board | **new**: holds conversations and draws every screen at 800 x 800 |
| Release files | `deepgram_agent-merged.bin`, `deepgram_agent.bin` | `deepgram_agent-esp32p4-merged.bin`, `deepgram_agent-esp32p4.bin` |

## Building for a board

```bash
idf.py set-target esp32s3     # or esp32p4
idf.py build
```

Changing the target throws away `sdkconfig` and the build folder. Everything a
board needs is selected from that one choice:

| What | Where |
|---|---|
| Config | `sdkconfig.defaults` for both boards, then `sdkconfig.defaults.esp32s3` or `sdkconfig.defaults.esp32p4` on top; IDF loads the second one by target |
| Components | `main/idf_component.yml`: the BSP, and on the P4 the Wi-Fi components, each behind a `target ==` rule |
| Lock file | `dependencies.lock` for the S3, `dependencies.lock.esp32p4` for the P4 (top-level `CMakeLists.txt`). Separate, so resolving one board never moves the other's versions |
| Code | `main/board.h`: the BSP header, plus the few facts the code branches on (`BOARD_PANEL_CO5300`, `BOARD_PANEL_SIZE`, `BOARD_PM_MIN_FREQ_MHZ`, `BOARD_BOOT_GPIO`) |

Code outside `board.h` should test those facts, not the chip name. The facts
say what differs; the chip name doesn't.

## One layout, two panel sizes

Every drawn screen was designed in 1:1 pixels on the S3's 466 px panel, and
the numbers in the code are those pixels. `main/ui_scale.h` scales them to the
board's panel: `PX()` for whole pixels, `PXF()` for distances. The P4 shows the
same picture at 800/466, about 1.72 times the size. Both macros are exact at
466, so the S3 compiles to the code it had before they existed; this was
checked by comparing its code sections with the earlier build, byte for byte.

- **New drawing code:** write the design's 466 px numbers inside `PX()` or
  `PXF()`. `PANEL_C`, `PANEL_R` and the other constants in `panel_geom.h` and
  `clock_face.h` already scale.
- **Fonts:** use the role names in `main/ui_fonts.h` (`FONT_PANEL_M`,
  `FONT_STATUS`, ...), never a font by size. Each board compiles its own set,
  generated by `lv_font_conv` at its scale; each file's header has the command.
- **What does not scale:** touch thresholds (swipe distance, edge bands, tap
  slop, hit slop). A finger is the same size on both boards, and the two panels'
  pixel densities are within 15 %. One-pixel antialiasing ramps don't scale
  either.
- **Checks:** `host/panel.sh` and `host/clock.sh` build and run at both sizes.
  On the board, the bench self-tests (`CONFIG_UI_PANEL_SELFTEST`,
  `UI_CLOCK_PREVIEW`, `UI_STOPWATCH_SELFTEST`, `UI_ECHO_SELFTEST`,
  `UI_RING_SELFTEST`) capture every screen for `host/shot2png.py`.

## The ESP32-P4 board

### Chip revision

The board tested so far has **P4 revision v1.3**. IDF 5.5.5 builds for revision
3.1 and later by default, and that image does not boot on v1.x. The two are
incompatible in both directions, so `sdkconfig.defaults.esp32p4` selects
`CONFIG_ESP32P4_SELECTS_REV_LESS_V3` and the build runs on v1.x boards only.
`esptool.py chip_id` prints the revision. A board with v3.x silicon would need
its own build.

### Wi-Fi through the C6

The P4 has no radio. Wi-Fi runs on the ESP32-C6 next to it, and the P4 drives
it over SDIO through `esp_hosted` and `esp_wifi_remote`. The `esp_wifi_*` calls
in this repo are unchanged, and the setup portal works over the link too.

**The host components are pinned to `esp_hosted 1.4.*` and
`esp_wifi_remote 0.14.*`**, the versions Waveshare's own examples use. The C6
ships with esp_hosted firmware that reports version `0.0.0`. Against it, host
3.1.0 connects, scans and raises the setup network, then stalls every TLS
handshake: the C6 sends frames of 2-3 kB, and that host drops anything over
1536 B. No host setting fixes it. The pin stays until the C6 firmware is
updated.

**The SDIO bus runs at 20 MHz, not the 40 MHz default.** At 40 MHz the link
stalled under steady agent traffic: `send queue full`, then
`Could not lock ws-client`, then no DNS or TLS at all, while the C6 still
reported that it was connected. Back-to-back sessions of about 40 s each on one
access point:

| SDIO clock | Display | Result |
|---|---|---|
| 40 MHz | off | 9 sessions, then the stall |
| 40 MHz | full-screen redraws | 2 sessions, then the stall; it never recovered |
| 20 MHz | full-screen redraws | 19 of 19 over 15 minutes |

An S3 on the same access point was clean throughout. The stall matches
esp-hosted-mcu issue #221. 20 MHz on 4 lines carries about 10 MB/s, against the
agent's ~64 kB/s.

**The repo's lwIP settings matter here too.** Without the larger TCP send buffer
and window in `sdkconfig.defaults`, every 20 ms audio send blocked ~160 ms and
the uplink ran at about half real time. That looks like a link fault, and it
isn't one.

### When the C6 wedges

**A few hours into uptime, the C6 can stop passing traffic.** This happens
with the device idle, with no log line, and it doesn't recover. A bench left
running caught it twice in one day, in two forms:

- **It stays associated at full signal.** Nothing reaches even the gateway.
- **Traffic fades out, then the association drops.** Every rejoin after that
  fails, with reasons 2 and 205: 637 tries over 6 hours, while the access point
  served everyone else.

Both times the C6 still answered control calls.

**Rejoining doesn't clear it, but a reset of both chips does**, in about 5 s,
on the same access point with the same MAC. A tap during a wedge fails with
`CANNOT_RESOLVE_HOSTNAME`.

**`CONFIG_WIFI_WEDGE_RESET` (default on, P4 only) is the recovery.**
`main/wifi_wedge.c` resets the board when either form shows:

- **Refused rejoins:** they go on for 3 minutes.
- **A dead gateway:** it answers none of three pings, twice in a row. The
  check runs every minute, and at once when a session's socket fails.

It doesn't reset in these cases:

- **The router is switched off.** That gives reason 201, no AP found, which the
  reconnect loop waits out as before.
- **The gateway never answers pings.** Failures only count once that
  connection has proven itself, with the gateway answering a ping or a
  session reaching Deepgram (`EVT wifi wedge check armed`).

**Repeat resets back off**, from 5 minutes, doubling to an hour. Each step
logs an `EVT wifi wedge` line, and TLM carries the count as `wd=`.

**The trigger is Wi-Fi 6 (802.11ax).** On 802.11ax the factory C6 firmware
fails for hours at a time, then works again. During those periods it fails in
two ways:

- **A few seconds into a session's audio uplink, it stops sending.** You see
  `send queue full`, then the socket fails, while frames still arrive from the
  access point.
- **The link dies while idle**, often within two minutes of boot. Rejoins are
  then refused with reasons 2 and 205, as in the wedges above.

Before the A/B test, these were ruled out on the bench: the P4 firmware (the
release build failed too), the SDIO clock, the access point (two of them, and a
phone hotspot), USB power against a wall charger, and the speaker. An S3, which
has no 802.11ax, held its sessions in the same spot.

**A 12-hour A/B settled it** (2026-11-19 to 11-20). The bench switched
between the two settings every 5 minutes, and reset both chips at the start
of each cycle, so each setting ran on a fresh C6 in the same conditions:

| Setting | Cycles | Cycles with a failure |
|---|---|---|
| b/g/n/ax | 72 | 34 |
| b/g/n | 72 | 0 |

The failures came in three periods: 21:00–02:00, 03:30–04:50 and once at 05:20.
The b/g/n cycles interleaved with them were all clean, including the 42 right
beside a failing 802.11ax cycle. The bench command `proto ax|bgn`
(`CONFIG_BENCH_NET_PROBE`) does the switching. It's kept across a software
reset, so `proto bgn` then `reboot` boots on b/g/n.

**`CONFIG_WIFI_STA_NO_11AX` (default on, P4 only) joins with b/g/n.** The
protocol is set explicitly either way and read back, and the boot log shows it
as `EVT wifi protocol set 0x07 ... read back 0x07`. 802.11ax adds little on
2.4 GHz for a ~32 kB/s audio stream.

**The watchdog stays.** The wedges caught on 11-18 were on 802.11ax too, and
they match the idle failures above. But nothing has yet run long enough on
b/g/n to show those can't happen there, so the watchdog stays as the backstop.

### Updating the C6 firmware

Not done, and not needed while b/g/n holds. A newer C6 firmware might fix
802.11ax, but nothing here needs it. If the stall comes back on b/g/n, the next
step is esp_hosted 2.x on both ends: the C6 firmware and the host components
together, then removing the pin. What's known so far:

- **The safe route is the C6's own UART** (header J4: U0TXD, U0RXD, GND, IO9).
  It allows a backup of the factory image first, and recovery if the new one
  doesn't boot.
- **An update from the P4 over SDIO works on the factory `0.0.0` firmware**
  (esp-hosted-mcu #143), but it has no rollback. A C6 image that doesn't boot
  leaves the board without Wi-Fi until J4 is reached.
- **Build the C6 image for DIO flash, not QIO.** #143 records a bricked C6 from
  that mistake.

### Memory and flash

**`CONFIG_SPIRAM_XIP_FROM_PSRAM` is required.** The panel's frame buffer is in
PSRAM. Without XIP, every flash erase switches the cache off for tens of
milliseconds. The conversation history erases one sector per agent sentence,
and the panel flashed near-white each time. No DSI underrun is logged, and the
frames LVGL draws are correct, so neither looks wrong in the log; count flashes
against `history_store: saved` lines instead. The S3 has always had this
setting, for its own reasons.

### Power

- **No battery.** The board has no fuel gauge in its BSP, so `CONFIG_BATTERY` is
  off: no charge dots, and the agent's battery tool is compiled out.
- **Always on external power.** With no battery, none of the battery's power
  saving runs: the sleeping clock stays at full brightness, at 10 fps
  (`BOARD_CLOCK_EXT_FRAME_MS`), and never dims or goes off. 30 fps was tried:
  a clock frame at 800x800 draws in about 36 ms, and the panel managed 12.7 fps
  with the display task saturated.
- **No light sleep.** Tickless idle is off, and deep idle goes with it. Light
  sleep with the SDIO link up has never been measured.
- **The CPU stays at 360 MHz.** The power manager's floor equals its ceiling
  (`BOARD_PM_MIN_FREQ_MHZ`), because the S3's 80 MHz floor is not a valid
  frequency on the P4.

### Console and setup

- **Console:** UART0 through a USB-UART bridge at 1 000 000 baud (GPIO 37/38).
  Opening the port resets the board, even with DTR and RTS held low.
- **Setup network name:** built from the base MAC, because the P4 has no Wi-Fi
  MAC of its own. It reads `dg-agent-XXXX` like the S3's.
- **Backlight:** the BSP starts it at 0 %, so `ui.c` sets the brightness
  explicitly.
